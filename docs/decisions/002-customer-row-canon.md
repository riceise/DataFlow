# ADR-002: канон строки Customer (v1)

Статус: принято, этап 7 / пакет A.

Нормализация и проверка строки выполняются синхронно по **снимку схемы задания**.
Вход — общий `ParsedRow`, независимый от CSV/XLSX: физический номер, исходные
значения, JSON исходных ячеек, признак пустой строки и ошибки парсера.
Пустую физическую строку определяет парсер. Запись из явных пустых ячеек является
строкой данных и проверяется на required. Пробелы по краям значений удаляются
`string.Trim()`; пустое значение становится null. Регистр строк, включая email,
сохраняется: текущий формат схемы не содержит правила изменения регистра.
Значения boolean принимаются только как `true` / `false`, дата — строго ISO
`yyyy-MM-dd` с invariant culture и проверкой календаря.
Правила длины применяются после trim; длина измеряется в UTF-16 code units,
как в существующей .NET-валидации схемы/API.

## Канон и SHA-256

Каноническое представление содержит **все пять** полей Customer в порядке:
`externalId`, `name`, `email`, `registeredAt`, `isActive`.
Порядок задан `JsonPropertyOrder`, имена — `JsonPropertyName`; порядок входных
полей, версия и порядок схемы, источник и номер строки на канон не влияют.
Используется System.Text.Json с закрытыми опциями:

- `JavaScriptEncoder.Default` (стандартное escaping Unicode и HTML-символов);
- `WriteIndented = false`, `PropertyNamingPolicy = null`;
- `DefaultIgnoreCondition = Never`: null всегда записывается явно;
- дата сериализуется строкой `yyyy-MM-dd` с `InvariantCulture`;
- boolean — JSON boolean, текст — JSON string;
- отсутствующая/пустая optional-дата всегда `"registeredAt":null`, в том числе
  когда это поле вообще отсутствует в схеме.

`RowHash` — SHA-256 UTF-8 байтов канона **без BOM и завершающего перевода строки**,
64 шестнадцатеричных символа в нижнем регистре. Hash вычисляется только для
валидных строк. Канон и SHA закреплены literal golden-тестами, включая Unicode,
HTML-escaping, null, дату и разные культуры. Изменение протокола требует нового
решения и анализа совместимости существующих Customer/RowHash.

## NaturalKey и повторы внутри файла

Ключ вычисляется после нормализации по `keyFields` snapshot. Текущий API MVP
разрешает только `externalId`; сохраняется уже принятый в домене формат:
`{DataSourceId:N}:{ExternalId.Trim()}`. Сравнение ключей — ordinal, case-sensitive.
Вспомогательная функция поддерживает явно заданные Customer keyFields: их
имена/значения сериализуются с ordinal-сортировкой имён и теми же JSON-опциями,
затем используется `sha256:{DataSourceId:N}:{SHA256(keyJson)}`. Этот же bounded
формат используется для слишком длинного externalId у невалидной строки;
разделитель не даёт коллизий составных ключей, длина укладывается в индекс 256.
Правила API источников этим не расширяются.

`CustomerFileRowProcessor` создаётся отдельно для каждого файла, хранит только
`HashSet<string>` ключей и может принять ранее закоммиченные ключи. Первая строка
с пригодным ключом резервирует его **даже при ошибке другого поля**; повтор
становится Invalid с кодом `duplicate_key_in_file` независимо от остальных
значений. Непригодный/отсутствующий ключ не резервируется. У Invalid остаётся
пригодный NaturalKey для будущего восстановления множества; Customer/RowHash
не возвращаются. Исходные данные остаются в ParsedRow для сохранения RawData
батчем. Ошибки содержат только field/code/безопасное сообщение, без значений.
